# 由 Agent 引导的安装

这份文档写给**正在协助用户安装本插件的 Agent**。目标：让用户在不泄露 `app_secret` 的前提下，
把飞书机器人接到 DSH 上并跑通。

---

## 铁律

违反任何一条都算安装失败，即使功能最终能用。

1. **不要让用户把 `app_secret` 贴进对话。** 对话内容会进入会话记录、日志、可能的备份。
2. **不要让密钥出现在命令行参数里**（如 `--secret xxx`），它会进 shell 历史。
3. **不要自己替用户创建飞书应用**，也不要索取用户的飞书账号密码。
4. **不要把 `app_secret` 写进仓库内的文件**。凭据只能落在 `~/.dsh-im-bridge/gateway.json`。
5. **同一个飞书应用只允许一个长连接消费者**。如果有别的程序也在连这个应用，必须二选一，
   否则事件会被两边分摊，各收一半。

合法的密钥入口只有两个：

```bash
node tools/setup-feishu.mjs        # 交互式：输入不回显，自动收紧文件权限
```

或用户自己在系统里设置 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 环境变量（插件优先读环境变量）。

---

## 推荐路径：扫码创建（走飞书的设备码授权）

本插件已经实现了飞书的设备码注册流程（RFC 8628），**用户只需扫码，无需去开放平台手动建应用，
密钥也不会经过对话**。

你（Agent）要做的是：

1. 让用户在本机执行：

   ```bash
   node tools/feishu-setup-qr.mjs
   ```

2. 工具会打印一个 `https://open.feishu.cn/page/launcher?user_code=XXXX-XXXX` 形式的链接，
   把它原样交给用户，让用户用手机飞书扫码或直接打开，按提示确认创建应用。

3. 等待用户在飞书里确认。工具会轮询，拿到凭据后自动写入 `~/.dsh-im-bridge/gateway.json`
   （权限收紧），并打印掩码后的结果。**你不需要、也不应该索取 `app_secret`。**

4. 国际版账号加 `--lark`。若用户扫错区域，工具会自动切换域名。

如果用户不希望自动写盘，可加 `--no-write`，由用户自行填写（见下面的手工路径）。

## 手工路径（备用）

若扫码流程因网络或组织策略不可用，让用户自行在飞书开放平台创建自建应用，
再用 `node tools/setup-feishu.mjs` 写入凭据（隐藏输入）。



---

## 手工路径的详细步骤（仅在扫码不可用时）

每一步都先确认完成，再进行下一步。不要并联跳过。

### 1. 创建应用并写入凭据

优先走扫码流程（见上一节）：让用户运行 `node tools/feishu-setup-qr.mjs`，把打印出的链接交给用户，
等他确认。

若该流程不可用，改用下面的手工步骤：让用户在 `https://open.feishu.cn/app` 创建「企业自建应用」，
然后依次完成「开启机器人能力」「开通权限」「事件订阅选长连接」「发布版本」，最后用
`node tools/setup-feishu.mjs` 写入凭据。

### 2. 开启机器人能力

应用详情 → 「添加应用能力」→ 启用**机器人**。

### 3. 开通权限

「权限管理」里至少开通：

| 权限 | 用途 |
|---|---|
| 获取与发送单聊、群组消息 | 收发消息 |
| 以应用身份发消息 | 机器人回复 |
| 读取用户发给机器人的单聊消息 | 接收用户消息 |

按提示提交，需要管理员审核的组织要先完成审核。

### 4. 事件订阅方式选「长连接」

「事件订阅」→ 选择**长连接**（不是 Webhook）。本插件从本机主动连出，不需要公网地址、端口映射或内网穿透。

订阅事件：**接收消息 v2.0**（`im.message.receive_v1`）。

这一步选错是安装失败最常见的原因：选成 Webhook 时，插件能连上但收不到任何消息，
表现为“发消息完全没反应”。

### 5. 发布版本

「版本管理与发布」→ 创建版本 → 申请发布。企业内应用通常需要管理员在管理后台通过审核。

未发布的应用，机器人不会出现在用户的飞书里。

### 6. 写入凭据

扫码流程已经自动完成这一步。若走手工路径，请让用户在本机终端里执行：

```bash
node tools/setup-feishu.mjs
```

然后按提示输入 `app_id` 与 `app_secret`（输入不回显，只显示 `*`）。工具会自动：
写入 `~/.dsh-im-bridge/gateway.json`、把文件权限收紧到当前用户、并把 `enabled` 置为 `true`。

用户若想改用环境变量，可自行设置后跳过此步。

### 7. 重启 DSH

配置在插件启动时读取，必须重启桌面 App。

### 8. 验证

```bash
node tools/setup-feishu.mjs --show     # 应显示 enabled=true、appId、掩码后的 secret
```

然后在飞书里给机器人发 `?status`，应立刻收到一条自检信息（不触发模型调用）。
再发一句普通消息，应收到回复。

首次回复前，插件会把该聊天的映射打印到日志，让用户把它填进 `config.json` 的 `sessionKeys`：

```
pin it with: "sessionKeys": { "feishu:oc_xxx:ou_yyy": "<会话 id>" }
```

---

## 判断树

| 现象 | 先查什么 | 处理 |
|---|---|---|
| 日志里没有 `gateway: running in-process` | `gateway.json` 是否存在、`enabled` 是否为 `true`、凭据是否写入 | 让用户重跑 `setup-feishu.mjs`，重启 DSH |
| 日志有启动行，但发消息无任何反应（连表情都没有） | 事件订阅是否选了**长连接** | 改成长连接并重新发布版本 |
| 收到消息但无回复 | 是否已给机器人开通「发送消息」权限；是否还有其他进程连着同一应用 | 补权限；停用另一个消费者 |
| 回复是 `❌ 桥接失败：session not in allowSessions` | 目标会话是否在白名单 | 让用户把会话 id 加进 `config.json` 的 `allowSessions` |
| 回复是 `❌ 桥接失败：…a proper resume is unavailable` | 该会话是否在桌面打开 | 打开对应会话 |
| 回复里 `##`、`**` 原样露出 | `replyFormat` 是否为 `text` | 改回 `card` |
| 其他用户也能用这个机器人 | `allowUsers` 状态 | 让用户把首个发送者的 `open_id` 写进 `allowUsers` |

---

## 交付给用户的话术要点

- 密钥只在本机文件里，仓库与 npm 包都不含凭据。
- 如果 `app_secret` 曾经出现在聊天、截图或日志里，建议在开放平台重置一次，然后用
  `setup-feishu.mjs` 重新写入。
- 桌面 App 必须开着，插件住在它的进程里。
- 想清理时删掉 `~/.dsh-im-bridge/gateway.json` 并把 `enabled` 置为 `false` 即可断开。
